# Product Requirements Document (PRD)
## Student Transport Routing, Assignment and Daily Operations Platform

**Prepared for:** YottaFlex.ai Associate AI Forward Deployed Engineer, Round 2 Code Challenge  
**Document type:** Codex-ready product and engineering specification  
**Recommended implementation:** Python, Streamlit, SQLAlchemy and SQLite  
**Default synthetic-data seed:** `20261022`  
**Status:** Build specification

---

## 1. Product summary

Build a locally runnable application that helps a school transport administrator assign students to approved pickup stops and bus routes, check operational constraints, record daily attendance, handle missed pickups, notify guardians through a simulated notification channel, and review exceptions with a traceable audit history.

The application must demonstrate the complete workflow using synthetic data. It must generate the required full-scale dataset of **5,000 students, 100 buses, 300 stops and 200 school days**, while also supporting a smaller starter dataset generated by the same parameterized code.

The system must make decisions explainable. A reviewer should be able to see why a student was assigned to a stop and route, why an assignment was rejected or flagged, how attendance affected notifications, and how reported metrics were calculated from persisted records.

This is a deterministic operations and data-engineering project. A runtime LLM is not required. AI coding tools may be used during development, but their prompts and use must be disclosed in the repository.

## 2. Problem statement

Schools need to allocate students to routes and pickup stops while respecting:

- Bus capacity and capacity changes over time.
- Approved stops and approved student addresses.
- Student accessibility needs and accessible-vehicle availability.
- Student and stop pickup windows.
- Route sequence and realistic travel times.
- Daily attendance, absences, route disruptions and missed pickups.
- Guardian contact validity, notification consent and privacy.

The application must expose decisions and exceptions, preserve state changes as records or events rather than overwriting history, and produce measurable operational and data-quality outcomes.

## 3. Goals and success criteria

### 3.1 Goals

1. Generate a reproducible, relational synthetic dataset with consistent primary and foreign keys.
2. Build valid route candidates and assign students to approved stops and feasible routes.
3. Enforce capacity, accessibility, approval and time-window rules before confirming assignments.
4. Simulate 200 school days of attendance and route disruptions.
5. Create guardian notifications from attendance outcomes using synthetic contacts only.
6. Provide a visible exception workflow for the five required negative scenarios.
7. Preserve event history and provide traceability from a dashboard metric to its source records.
8. Export CSV, JSON and SQL seed data, along with documentation and validation results.
9. Prove fixed-seed reproducibility by generating the same dataset twice and comparing row counts and checksums.
10. Make the application easy for a reviewer to install, run and verify locally.

### 3.2 Success criteria

The submission is successful when:

- The starter dataset can be generated and loaded using documented commands.
- The full-scale generator produces the required entity volumes and 200-day attendance history.
- Baseline assignments pass all hard safety and capacity constraints.
- All joins and referential-integrity checks pass for the valid baseline.
- The five labelled negative scenarios are detected and receive the documented expected action.
- Attendance and notification metrics are derived from persisted events, not independently generated totals.
- Two runs using the same seed and parameters produce identical table contents and checksums.
- A reviewer can inspect routes, assignments, attendance, notifications, exceptions and validation results in the UI.
- The public repository contains clear setup instructions, tests or equivalent verification evidence, decision notes and complete AI prompt history.

### 5.1 In scope

- Synthetic master data generation: Student, GuardianContact, AddressZone, Stop, Bus and Driver.
- Dependent data generation: Route, RouteStop, Assignment, AttendanceEvent and Notification.
- Capacity-change, route-disruption and audit event records.
- Candidate route generation and deterministic route ordering.

- Constraint validation and actionable exception reporting.
- Daily attendance and missed-pickup simulation.
- Simulated guardian notifications; no real SMS, email or phone calls.
- Dashboard, searchable data tables and operational workflows.
- CSV, JSON, SQLite and SQL exports.
- Data dictionary, source manifest, validation summary, reproducibility report, tests and AI-use disclosure.

### 5.2 Out of scope

- Live GPS tracking, live traffic, road-network APIs or map-provider integrations.
- Real student, school, guardian, phone, email or address data.
- Real SMS/email delivery or integration with a messaging provider.
- Production authentication, payment, fleet maintenance or driver payroll.
- Machine-learning prediction or a runtime chatbot. Do not add an LLM dependency merely to make the project appear AI-related.
- Multi-school tenancy or cloud deployment. The required deliverable is locally runnable.

## 6. Product assumptions and implementation decisions

These are implementation choices to keep the challenge achievable and testable. Document any change in `docs/DECISIONS.md`.

1. **Technology:** Python 3.11 or newer, Streamlit for the local interface, SQLAlchemy for persistence, SQLite as the default database, pandas for tabular operations, and pytest for tests. Use a small number of common, free dependencies.
2. **Geography:** Use a synthetic two-dimensional coordinate plane measured in kilometres. Do not imply that coordinates correspond to real streets or locations. No external routing service is required.
3. **Travel-time model:** Estimate travel time from Euclidean distance, a documented road-distance multiplier and a configurable average speed. Add a fixed dwell time at each stop. All units must be explicit.
4. **School calendar:** Generate exactly 200 weekday service dates from a configurable start date. Do not use the current wall-clock time as generated business data.
5. **Baseline validity:** Generate a valid baseline first. Keep deliberately invalid cases in a separate scenario-fixture dataset. Do not contaminate valid operational tables to create anomalies.
6. **Assignment period:** Use the 2026 school year and the required assignment ID format `ASN-<student-id>-2026`. Keep assignment effective dates so a future reassignment does not erase the prior assignment.
7. **Notification delivery:** Simulate delivery and persist its result. Never call an external messaging service.
8. **Seed:** Use `20261022` by default. All random generation must come from explicitly seeded random-number generators.
9. **Scale modes:** Provide `starter` and `full` presets, plus custom size parameters. Both presets must call the same generator functions and rules.
10. **Generated artifacts:** Large full-scale outputs should be generated locally and excluded from Git. Include a small starter fixture or a command to generate it so the public repository remains reasonably sized.

## 7. Main user journeys

### Journey A: Generate and inspect the transport network

1. Platform administrator opens the Data Setup page.
2. Selects `starter` or `full`, seed and output location.
3. Runs master-data generation, dependent-record generation and baseline assignment.
4. Sees row counts, generated IDs, validation status and data-manifest information.
5. Opens the Data Explorer to inspect records and follow foreign-key relationships.

### Journey B: Plan routes and assign students

1. Academic administrator opens Route Planning.
2. Reviews route candidates, bus capacities, accessible-vehicle flags and planned stop sequences.
3. Runs the assignment engine.
4. Reviews assigned, unassigned and rejected students with a reason for each decision.
5. Opens a route to inspect its bus, driver, ordered stops, occupancy, capacity and estimated duration.
6. Confirms only assignments that pass all hard constraints.

### Journey C: Run a school day

1. Administrator selects a service date.
2. Runs the attendance simulation for that date.
3. Reviews picked-up, absent, late and missed-pickup outcomes.
4. The system creates notification records for eligible attendance events.
5. Support staff reviews any suppressed or failed notification and its reason.
6. The event and audit history remains available after later changes.

### Journey D: Review exceptions

1. Platform administrator opens the Exception Lab.
2. Runs the five required labelled scenario fixtures.
3. The rule engine detects each issue and records an observed decision.
4. The evaluation view compares the observed result with a separate ground-truth file.
5. The reviewer can inspect the evidence, expected action, observed action and pass/fail result.

### Journey E: Verify and export

1. Platform administrator runs data validation and reproducibility checks.
2. Reviews row counts, primary-key checks, foreign-key checks, rule violations and checksums.
3. Exports CSV/JSON/SQL seed data and a validation summary.
4. Uses the README commands to regenerate and verify the project from a clean checkout.

## 8. Functional requirements

Priority definitions: **P0** = required for a credible submission; **P1** = important; **P2** = polish if time permits.

### FR-01: Master-data generation (P0)

Generate the following parent/master entities before creating dependent records:

- Student
- GuardianContact
- AddressZone
- Stop
- Bus
- Driver

Requirements:

- Create synthetic student address details and zone assignments.
- Create approved and unapproved stops/addresses with explicit status fields.
- Generate bus capacities and accessibility capabilities.
- Generate drivers and their active/inactive state.
- Ensure all generated identifiers follow deterministic naming conventions.
- Keep each entity's primary key unique and immutable.
- Do not use real personal data or contactable guardian information.

### FR-02: Dependent record generation (P0)

Create, in dependency order:

1. Route candidates.
2. Ordered RouteStop records.
3. Student Assignment records.
4. Daily AttendanceEvent records.
5. Notification records.
6. Capacity-change, disruption and audit events.

All child records must use valid parent IDs. A relationship must be represented by a foreign key, not merely by copying a display name.

### FR-03: Route candidate generation (P0)

- Build route candidates from active buses, active drivers, approved stops and service zones.
- Each route must have exactly one assigned bus and one assigned driver for its effective period.
- A bus and driver cannot be double-booked for overlapping service periods.
- Route IDs must follow `ROUTE-2026-000001`.
- Each RouteStop must have a unique route sequence number.
- Calculate travel time between consecutive stops using the documented synthetic travel-time model.
- Store planned arrival/departure times and the calculated travel minutes.
- Mark route feasibility explicitly: `FEASIBLE`, `INFEASIBLE` or `DRAFT`.
- Do not publish an infeasible route as active.

### FR-04: Student-to-stop and route assignment (P0)

The assignment engine must:

1. Consider only active students with an approved address and valid service eligibility.
2. Consider only active, approved stops within the configured service radius.
3. Require the selected route to contain the selected stop.
4. Require an accessible bus and an accessible pickup stop when `accessibility_required = true`.
5. Check the student's pickup window against the planned stop arrival time and any configured tolerance.
6. Check the bus's effective capacity on the assignment date.
7. Reject duplicate active assignments for the same student and overlapping effective dates.
8. Record a reason code and human-readable explanation for accepted, rejected or unassigned decisions.
9. Preserve prior assignment versions when a student is moved; close the previous effective period and create a new immutable versioned record. The initial annual assignment uses the exact `ASN-<student-id>-2026` format; subsequent versions may append `-V02`, `-V03`, etc.
10. Use deterministic tie-breaking so a fixed seed and input order produce the same result.

Recommended candidate scoring, after hard constraints have passed:

`score = (distance_km * 1.0) + (projected_route_duration_minutes / 60.0 * 0.5) + (capacity_utilization_after_assignment * 2.0) + (stop_count_after_assignment * 0.1)`

Choose the lowest score. The weights are configurable constants and must be documented. Do not allow a low score to override a hard safety, approval, accessibility, time-window or capacity constraint.

Possible decision reason codes:

- `ASSIGNED_BEST_FEASIBLE`
- `NO_APPROVED_STOP_IN_RANGE`
- `NO_FEASIBLE_ROUTE`
- `ACCESSIBILITY_MISMATCH`
- `CAPACITY_LIMIT_REACHED`
- `PICKUP_WINDOW_CONFLICT`
- `ADDRESS_NOT_APPROVED`
- `STUDENT_INACTIVE`
- `DUPLICATE_ACTIVE_ASSIGNMENT`

### FR-05: Capacity management (P0)

- Bus capacity is a positive integer number of seats.
- Persist capacity changes in a `BusCapacityEvent` table with effective dates, old/new capacity and reason.
- Capacity checks must use the capacity effective on the service date, not only the current Bus value.
- Do not commit an assignment that makes a route exceed effective capacity.
- If a future capacity reduction would make a route overloaded, identify affected assignments and require reassignment or an explicit unresolved exception before the new capacity becomes active.
- Show occupancy, capacity and utilization percentage for every route.

### FR-06: Route feasibility and stop sequence (P0)

- Stop sequence numbers must start at 1 and increase without gaps for each route.
- Arrival must be before or equal to departure at the same stop.
- The next arrival must be no earlier than the previous departure plus the calculated travel time.
- Stop pickup windows must be respected within a configurable tolerance.
- The total route duration must not exceed the route's configured maximum duration.
- Negative travel times, impossible arrival times and invalid stop sequences must fail validation.
- Store calculated travel time and the inputs used so route feasibility can be explained.

### FR-07: Daily attendance simulation (P0)

- Support selection of a school service date and simulation of that day.
- Support generation of the complete 200-school-day history.
- Create one AttendanceEvent per active assignment per service date, unless the assignment is not effective on that date.
- Supported attendance states: `PICKED_UP`, `ABSENT`, `LATE`, `MISSED_PICKUP`, `EXCUSED`.
- Derive event outcomes from documented simulation rules, seeded attendance probabilities and recorded disruption events.
- Persist each day's outcome as an event. Do not update an older event to represent a later day.
- Prevent duplicate attendance events for the same assignment and service date.
- Record the event source, event time, status and reason.

### FR-08: Route disruptions (P0)

- Generate route disruptions such as road delay, temporary stop closure or vehicle delay.
- Persist each disruption with route, date, type, affected stop where applicable, delay minutes, status and resolution details.
- A disruption must affect calculated arrival times and may lead to `LATE` or `MISSED_PICKUP` outcomes according to documented rules.
- Disruptions must be reproducible for a fixed seed.
- A resolved disruption must remain in history; do not delete it.

### FR-09: Guardian notifications (P0)

- Create a notification for configured events such as `ABSENT`, `MISSED_PICKUP` or a severe route disruption.
- Use only synthetic GuardianContact records.
- Send only through a simulated channel. No external network calls.
- Require an active contact, valid synthetic channel data, `is_verified = true` and `consent_to_notify = true`.
- Store notification ID, event ID, contact ID, channel, template code, status, simulated send time, idempotency key and failure/suppression reason.
- Do not create a `SIMULATED_SENT` notification for an invalid, unverified or non-consenting contact.
- Mask contact values in standard UI views.
- Notification ID must follow `NOT-2026-000001`.

### FR-10: Event history and auditability (P0)

- Record consequential state changes as explicit records/events.
- Include actor role, entity type, entity ID, action, timestamp, reason and before/after values where relevant.
- Do not overwrite assignment history, attendance events, notification outcomes, capacity changes or disruption history.
- Expose a chronological history view for a student assignment and a route.
- Provide a clear link from each exception to the records that triggered it.

### FR-11: Exception Lab and negative scenarios (P0)

Provide a separate, repeatable scenario suite for all five required cases:

| Scenario | Fixture | Expected system decision |
|---|---|---|
| Bus capacity exceeded | Candidate assignment would make occupancy exceed effective bus capacity | Reject or hold the candidate; raise `CAPACITY_EXCEEDED`; do not commit it as a valid assignment |
| Student assigned to incompatible route | Student requires an accessible vehicle but candidate route's bus is not accessible | Reject assignment; raise `ACCESSIBILITY_MISMATCH` |
| Impossible stop travel time | A stop sequence has a travel-time or time-window contradiction | Mark route infeasible; raise `IMPOSSIBLE_TRAVEL_TIME`; do not activate route |
| Notification sent to invalid contact | Notification fixture refers to an invalid, unverified or non-consenting contact | Block simulated send; raise `INVALID_GUARDIAN_CONTACT`; record suppression/failure |
| Unapproved address exposed | A view or export attempts to reveal an unapproved address | Redact or deny access; raise `UNAPPROVED_ADDRESS_EXPOSURE`; log the attempt |

Implementation rules:

- Keep valid baseline data clean.
- Keep scenario inputs under a separate location such as `data/scenarios/`.
- Keep expected labels and expected actions in a separate `ground_truth.json` or `ground_truth.csv`.
- Do not pass ground-truth labels into the routing, attendance or notification decision functions. Ground truth is for evaluation only.
- Each scenario result must include `scenario_id`, `issue_type`, affected entity IDs, detection result, observed action, expected action, pass/fail and evidence references.
- Running the suite more than once must not duplicate operational records or change the baseline dataset.

### FR-12: Validation and data quality (P0)

Provide a validation command and a UI summary for:

- Primary-key uniqueness and ID-pattern checks.
- Foreign-key integrity and orphan checks.
- Required-field and allowed-enum validation.
- Date ordering and effective-date consistency.
- Assignment uniqueness and lifecycle transitions.
- Bus capacity reconciliation by route and service date.
- Accessibility compatibility.
- Stop approval and address approval rules.
- Route stop sequencing and travel-time feasibility.
- Attendance uniqueness and valid assignment/date relationships.
- Notification contact verification, consent and idempotency.
- Duplicate detection.
- Reconciliation between source records and displayed totals.

The validation output must include check name, records checked, pass count, fail count, severity, affected IDs and a human-readable explanation. Do not silently repair data during validation.

### FR-13: Metrics and reporting (P0)

Calculate metrics from persisted source records. Do not generate metric totals independently.

Required metrics:

- Total students and active students.
- Assigned students, unassigned students and assignment coverage percentage.
- Active routes, buses and approved stops.
- Average and maximum route capacity utilization.
- Number of capacity violations.
- Number of inaccessible-vehicle assignment violations.
- Percentage of feasible routes.
- Average planned route duration and travel minutes.
- Attendance counts and rates by service date and status.
- Missed-pickup count and rate.
- Absence count and rate.
- Notifications created, simulated sent, suppressed and failed.
- Notification eligibility/delivery rate.
- Open and resolved exceptions by issue type.
- Data-quality pass rate and reproducibility status.

For each metric, document its formula, denominator, source table(s), filters and treatment of inactive records. Display the selected service-date range and dataset scale near the metric.

### FR-14: Searchable data explorer (P1)

Provide paginated/searchable tables for all core entities. Allow a reviewer to open a record and inspect its related records through IDs and relationships. Avoid loading the full one-million-row attendance table into memory or rendering it all at once.

### FR-15: Export and manifest (P0)

Export:

- CSV for every core entity and extension event table.
- JSON records for every entity, or a documented JSON bundle.
- SQLite database file.
- SQL schema and seed data (`schema.sql` and `seed.sql`, or equivalent reproducible SQL export).
- `manifest.json` containing seed, parameters, generator version, table row counts, file names, checksums, and provenance.
- `validation_summary.json` containing all validation results.
- Separate ground-truth artifact for the required anomaly fixtures.

Do not include ground-truth labels in the normal input data bundle. Make the distinction explicit in the README and folder structure.

### FR-16: Reproducibility check (P0)

- Compare table row counts and deterministic content checksums.
- Produce a report showing parameters, row counts, checksums, equality result and any differences.
- Exclude non-deterministic timestamps, machine paths and log metadata from content checksums, or make them deterministic.
- A different seed should change generated data while preserving schema and validation rules.

Include:

## 9. Business rules and domain logic

### 9.1 Address and stop eligibility

- Every active student must have one active AddressZone.
- An address must be explicitly approved before it can be used for route assignment.
- A stop must be active and approved to be considered by the assignment engine.
- A student can only be assigned to a stop inside the configured maximum service radius.
- An unapproved address may exist as a synthetic record for testing, but it cannot be used for a valid assignment or exposed through standard UI views.

### 9.2 Capacity

- `capacity` means the maximum number of students seated on a bus for a service run.
- `assigned_occupancy` is the number of active assignments whose effective dates overlap the service date and whose RouteStop belongs to the route served by the bus.
- `capacity_utilization = assigned_occupancy / effective_capacity`.
- A valid baseline route must satisfy `assigned_occupancy <= effective_capacity` on every service date.
- Do not round utilization before checking the underlying integer counts.

### 9.3 Accessibility

- `accessibility_required = true` means the student can only be assigned to a route whose bus has `accessible = true`.
- An accessible bus may carry students who do not require accessibility support.
- A non-accessible bus or a non-accessible pickup stop must never be used for a student who requires accessibility support.
- Accessibility is a hard constraint, not a scoring preference.

### 9.4 Pickup windows

- Store times in a consistent local service-time format, with the timezone documented in configuration.
- A student's pickup window must overlap the selected stop window and the planned arrival time, within a configurable grace period.
- A route whose computed arrival cannot satisfy the window is infeasible for that assignment.

### 9.5 Travel-time calculation

Use a documented formula such as:

`road_distance_km = euclidean_distance_km * ROAD_DISTANCE_FACTOR`

`travel_minutes = ceil((road_distance_km / AVERAGE_SPEED_KMH) * 60)`

Add `STOP_DWELL_MINUTES` at each pickup stop. Set explicit defaults in configuration, for example road-distance factor `1.25`, average speed `25 km/h` and dwell time `2 minutes`. These are synthetic modelling assumptions, not real-world traffic claims. Keep them configurable and include the actual values in the manifest.

### 9.6 Attendance outcomes

The simulator must use the fixed seed plus documented rules. Example rules:

1. If the student is inactive or the assignment is not effective on the service date, do not create an attendance event.
2. If the student is marked excused by the scenario input, create `EXCUSED`.
3. Otherwise apply the seeded absence probability to decide `ABSENT`.
4. If not absent and the route disruption causes arrival after the configured pickup grace threshold, create `MISSED_PICKUP` or `LATE` according to the documented threshold.
5. Otherwise create `PICKED_UP`.

The actual implementation may use a different documented rule order, but the output must be derived from inputs and deterministic logic. Save the rule parameters in the manifest. Never choose a ground-truth anomaly label by random assignment.

### 9.7 Notification eligibility

- Create notification candidates only for configured attendance/disruption event types.
- A notification may be simulated as sent only when the contact is active, verified, has consented, has a supported channel and passes format validation.
- Otherwise record a suppressed/failed result and the exact reason.
- Use an idempotency key so rerunning a day's notification step does not send duplicate simulated notifications.

### 9.8 Lifecycle and history

Use explicit lifecycle states and effective dates. At minimum:

- Student: `ACTIVE`, `INACTIVE`, `WITHDRAWN`.
- Stop: `ACTIVE`, `INACTIVE`, `PENDING_APPROVAL`, `REJECTED`.
- Bus/Driver: `ACTIVE`, `INACTIVE`, `OUT_OF_SERVICE` where relevant.
- Route: `DRAFT`, `FEASIBLE`, `ACTIVE`, `DISRUPTED`, `INACTIVE`.
- Assignment: `ASSIGNED`, `SUSPENDED`, `ENDED`, `REJECTED`.
- Notification: `QUEUED`, `SIMULATED_SENT`, `SUPPRESSED`, `FAILED`.

Do not overwrite previous state. Insert a new event or audit record and update only the current-state projection where needed.

## 10. Data model

All tables require a primary key. All relationships require actual foreign keys. Use bridge tables for many-to-many relationships. Use ISO 8601 dates/timestamps in exports and document timezones. Database-level constraints should be supplemented with application validation.

### 10.1 Core entities and cardinality

| Relationship | Cardinality | Notes |
|---|---|---|
| AddressZone → Student | 1:N | Each student has one active home zone; a zone may contain many students |
| AddressZone → Stop | 1:N | A zone can contain/serve many stops |
| Student → GuardianContact | 1:N | One or more synthetic contacts per student; effective dates supported |
| Bus → Route | 1:N | A bus can serve routes over time, but cannot be double-booked for overlapping service periods |
| Driver → Route | 1:N | A driver can serve routes over time, subject to availability/duty constraints |
| Route → RouteStop | 1:N | One route has an ordered list of route-stop records |
| Stop → RouteStop | 1:N | A stop may be used by multiple routes; RouteStop is the bridge table |
| Route ↔ Stop | N:M | Implemented using RouteStop, never as an unvalidated array of stop IDs |
| Student → Assignment | 1:N | Historical assignments are retained; at most one valid active assignment per student/date |
| RouteStop → Assignment | 1:N | A route stop may serve multiple student assignments |
| Assignment → AttendanceEvent | 1:N | One event per active assignment per service date |
| AttendanceEvent → Notification | 1:N | An attendance event may notify one or more eligible guardians |
| Bus → BusCapacityEvent | 1:N | Effective-dated capacity changes |
| Route → RouteDisruptionEvent | 1:N | Multiple disruptions may occur over a route's lifetime |
| Entity → AuditEvent | 1:N | Generic audit history references an entity type and ID; enforce valid references in application code |

### 10.2 ID conventions

Required formats:

- Student: `STU-000001`
- Stop: `STOP-000001`
- Bus: `BUS-000001`
- Route: `ROUTE-2026-000001`
- Assignment: `ASN-STU-000001-2026`
- Notification: `NOT-2026-000001`

Recommended additional formats:

- AddressZone: `ZONE-000001`
- GuardianContact: `GUA-000001`
- Driver: `DRV-000001`
- RouteStop: `RSTOP-000001`
- AttendanceEvent: `ATT-2026-000001`
- BusCapacityEvent: `BCE-2026-000001`
- RouteDisruptionEvent: `RDE-2026-000001`
- AuditEvent: `AUD-2026-000001`

Counters are zero-padded and deterministic. IDs must not change when a record is edited. Do not generate foreign keys independently; reference the exact parent ID.

### 10.4 Relationship and lifecycle constraints

- Use actual SQL foreign keys and enable SQLite foreign-key enforcement.
- Add unique constraints for natural combinations such as `(route_id, sequence_no)`, `(route_id, stop_id)` where duplicates are not valid, `(assignment_id, service_date)` and `idempotency_key`. A student's assignment versions must not have overlapping active effective periods.
- Add indexes on foreign keys and common filters: service date, status, route ID, student ID, bus ID and stop ID.
- Enforce at most one effective active assignment per student on a service date in application validation. SQLite partial indexes may be used where suitable, but tests must still verify date-range overlap.
- A Notification's guardian must belong to the same student as the AttendanceEvent's Assignment.
- A RouteStop's stop and route must both be active for the service date.
- A Route's bus and driver must be available and not double-booked.
- Preserve old records when a route, stop, bus, driver, assignment or contact changes state.

## 11. Synthetic data generation specification

### 11.1 Required volumes

Full scale:

| Entity / dimension | Target |
|---|---:|
| Students | 5,000 |
| Buses | 100 |
| Stops | 300 |
| School service days | 200 |
| Address zones | Parameterized; recommended 20–40 |
| Drivers | At least 100 active drivers for one route per bus |
| Guardian contacts | At least one per student; a portion with a second contact |
| Routes | 100 route candidates in the baseline, subject to availability |
| Route stops | At least 300 route-stop links; additional links allowed only when justified |
| Attendance events | One per effective active assignment per service day |

The generated attendance history will normally be approximately one million events when all 5,000 students have an active assignment for all 200 days. Exact totals must be calculated from effective assignments and school dates.

### 11.2 Starter preset

Recommended starter preset for quick local runs:

- 250 students
- 10 buses
- 30 stops
- 10 school days
- Proportionally scaled zones, drivers, guardian contacts, routes and events

The starter preset is a smaller parameter set, not a separate generator. It must exercise the same rules and code paths as full scale.

### 11.3 Generation order

1. Initialize deterministic RNGs from the supplied seed.
2. Generate AddressZone records.
3. Generate Bus and Driver records.
4. Generate approved and unapproved Stop records linked to zones.
5. Generate Student records with synthetic addresses, coordinates, pickup windows and accessibility needs.
6. Generate GuardianContact records linked to students.
7. Generate Route candidates with one bus and driver each.
8. Generate ordered RouteStop records and travel-time calculations.
9. Run assignment logic and persist valid assignments plus explicit unassigned/rejected decision outcomes.
10. Generate effective-dated capacity changes.
11. Generate route disruptions for school service dates.
12. Simulate attendance from active assignments and the event inputs.
13. Generate eligible simulated notifications.
14. Write audit events, exports, manifest and validation output.
15. Generate negative scenario fixtures and separate ground-truth labels.

### 11.4 Realistic distributions and meaningful variation

Use configurable, documented distributions rather than uniform values everywhere. For example:

- Student grade mix distributed across grades 1–12.
- Accessibility need rate in a small but meaningful range, with enough accessible buses/capacity to serve all baseline demand.
- Bus capacities varied within a plausible synthetic range, while total and accessible capacity remain sufficient for valid baseline assignments.
- Student coordinates concentrated around their assigned zone/stop with modest variation.
- Pickup windows drawn from a small set of realistic morning windows.
- Guardian contacts: mostly one primary contact, with a smaller share having a second contact.
- Absence and disruption rates configurable and documented.
- Approved/unapproved stop and address records represented explicitly.
- Active/inactive records represented without violating FK integrity.

The generator must allocate enough seats overall and enough accessible seats so the valid baseline can assign every eligible student. Do not silently increase capacity after an assignment fails. Report the total and accessible capacity before assignment.

### 11.5 School calendar

- Generate exactly the requested number of weekdays from `start_date` (default may be `2026-01-05`).
- Skip Saturday and Sunday.
- If a holiday calendar is added, keep it synthetic and deterministic, and document it.
- The service date list is a source table/list used by attendance simulation; do not independently generate event dates in multiple modules.

### 11.6 Determinism

- Use `random.Random(seed)` and/or an explicitly seeded NumPy Generator. Do not use module-global random state.
- Avoid non-deterministic iteration over sets or unordered database results. Sort by stable IDs before decisions and exports.
- Use deterministic timestamps for generated records, based on service dates and configured simulation times.
- Sort CSV/JSON exports by primary key or a documented stable key.
- Normalize JSON key order and CSV newline/encoding settings before checksumming.
- Keep machine-specific paths and actual execution timestamps out of content checksums.
- Store the seed, scale parameters, simulation probabilities, travel-time constants and generator version in `manifest.json`.

### 11.7 Anomaly fixture isolation

Keep these separate:

```text
 data/
   generated/             # normal baseline exports; ignored by Git
   scenarios/
     edge_case_inputs.json
   ground_truth/
     edge_case_ground_truth.json
```

The business-logic modules must not load or inspect `ground_truth`. Only the scenario evaluation layer may read it after decisions have been produced.

## 15. Non-functional requirements

### Reliability

- A failed generation step must report the failure and avoid leaving a partially valid database presented as complete.
- Use transactions or staged output directories and promote output only after successful validation.
- Re-running a command must have documented, safe behavior. Never silently append duplicate generated records.
- Surface actionable errors rather than raw stack traces in the UI; retain technical details in local logs.

### Performance

- Starter generation should be suitable for quick iterative development.
- Full-scale generation must handle approximately one million attendance events without requiring a hosted service.
- Use bulk inserts, indexes, pagination and aggregate queries where appropriate.
- Do not render or load the complete attendance history into a single UI table.
- Record actual generation and validation durations in the run report. Treat performance targets as measured outcomes, not unsupported claims.

### Security and privacy

- Synthetic data only. Use `.invalid` for synthetic email addresses and non-routable phone placeholders.
- No secrets, API keys, credentials, real personal data or proprietary code in the public repository.
- No outbound messaging or external calls are needed for the core workflow.
- Restrict unapproved address details and mask guardian contacts.
- Keep the role selector clearly identified as a demo simulation, not production authentication.

### Maintainability

- Type hints for public service functions.
- Small, cohesive modules and meaningful names.
- Centralized configuration and enums.
- Tests for business rules and negative paths.
- Explain non-obvious decisions in code comments and `docs/DECISIONS.md`.

### Portability

- Run locally on a typical developer laptop.
- Avoid paid services, GPU requirements, unusually large dependencies and internet-dependent runtime behavior.
- Provide Windows and macOS/Linux setup notes where commands differ.

## 19. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Full one-million-event generation is slow | Use bulk inserts, deterministic batching, indexed foreign keys and starter mode for development |
| SQLite export becomes large | Keep generated data outside Git; provide a starter dataset and reproducible command |
| Invalid examples contaminate valid baseline | Store negative fixtures and ground truth separately; test the separation |
| Capacity or accessibility edge cases are missed | Enforce hard constraints in one assignment service and test both positive and negative paths |
| Route timing is unrealistic | State clearly that the coordinate and travel-time model is synthetic; keep its formula configurable |
| Re-running simulations duplicates events | Add unique constraints and deterministic idempotency keys; make operations idempotent |
| UI becomes slow with large attendance history | Query aggregates, paginate rows and filter by service date/route |
| AI-generated implementation is not understood | Keep a decision log, prompt history and manual walkthrough notes; candidate reviews and validates the core logic |
| Public repository leaks sensitive information | Use synthetic-only fixtures, `.invalid` email addresses, no secrets and a pre-submission scan |
